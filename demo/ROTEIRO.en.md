# Demo script — 10 minutes

> Source of every number: `demo/numbers.json`, generated by `collect_numbers.sh` from the tables.
> Before you start: `PROFILE=<your-profile> ./reset_demo.sh`, then open the console.
> Legend: **[scene]** marks a cut for recording · **[click]** marks the action on screen.

---

## 1. The problem

**[scene: the job page in Databricks]**

This sales job used to run in under three minutes. It now takes twenty-six.

The Spark UI shows that. It shows the duration, the stages, and that one task took far longer
than the others. What it does not answer is what matters: why it changed, what changed, who is
affected and what it cost.

Today that question is answered by a person opening five tabs — Spark UI, run history, Git,
catalog and billing — and cross-referencing everything by hand. It takes from thirty minutes to
a few hours, and the answer depends on who happens to be on call.

That is the work this platform does.

## 2. The incident

**[scene: EICT console, incident list]**

**[click: open the top incident]**

Two slow runs produced **one** incident, not two. The correlation key is the job plus the
problem type, so a repeat becomes a new timeline entry rather than a new alert. That is the
difference between monitoring and operating: the operator sees a problem, not a flood.

**[optional live click: run `./trigger_recorrencia.sh` in a second terminal]**

While we talk, I just triggered a slow run on a smaller job. In a few minutes it shows up here
as a recurrence — on that job's incident, not this one. Worth saying out loud: that incident
will carry three pieces of evidence, because there is no commit attached. The full story is
this one.

---

## 3. The diagnosis

**[scene: hypothesis section, first hypothesis expanded]**

The top hypothesis reads: skew on the join key introduced by a code change. It sits at **0.9**
confidence, backed by four pieces of evidence. Let me read all four, because the value is in
them, not in the score.

**First, the data.** A single customer holds **40** percent of the rows — **24** million out of
**60** million. That imbalance was always there.

**Second, the execution plan.** The slow run contains a `Window` operator that the healthy run
did not have. Spark does not split window partitions; the hot key became one giant task.

**Third, the change.** The commit that introduced that window is identified, along with the file
it touched.

**Fourth, and most important: input volume did not change.** Same number of rows, before and
after. That **rules out** the most common explanation — "the data grew" — and it is what turns
correlation into a diagnosis.

---

## 4. Why this is not a guess

**[scene: alternative hypotheses]**

**[click: expand the next two hypotheses]**

The alternatives stay listed at **0.05**, each with the evidence that knocks it down: the
execution environment is identical to the healthy run, and the volume is the same. A tool that
only shows the right answer cannot be audited; this one shows what it considered and why it
discarded it.

Note the ceiling. No hypothesis goes above **0.9** — that is the limit for inference without
human confirmation, and it lives in the code, not in a guideline. When someone clicks "confirm
cause", the record gains an owner and becomes knowledge.

---

## 5. Impact and cost

**[scene: impact section]**

The incident points to **3** affected assets: the output table, the job, and the sales dashboard
that consumes that table. This comes from catalog lineage, not from manual configuration.

**[click: cost card]**

And the incremental cost of this run: **0.0682** dollars. That sounds small, and it is — this is
a demo. The point is the mechanism: the value comes from the billing table, and while billing
has not arrived, the field reads unavailable. Never estimated.

---

## 6. The guardrail

**[scene: incident summary]**

Finally, the text you read at the top. It was written by rule, not by the language model.

The model did answer, but the answer was **rejected** in validation, because it did not follow
the required format — every sentence must cite the identifier of an evidence item that exists.
Without that, the platform discards it and writes the deterministic text.

That is the principle holding up everything else: evidence before inference. The AI drafts;
what counts as true is decided by rules and by a person.

**[final scene]**

The code is open, with **100** tests and **96** percent coverage on the domain core. And,
honestly, **8** of the most interesting problems only showed up running for real — no local test
would have caught them.
